## 1. 現状の問題（前版から維持）

2026-07-30時点の画面を確認した結果、次の問題を確認した。前版3節の指摘は有効であり、そのまま引き継ぐ。

1. **視覚的階層が存在しない** — FPSモニタ、8本の緑スライダー、4枚の同一意匠パネル、キャンバスがすべて同じ強さで並んでいる
2. **右ドックの縦スクロール依存** — ウィンドウ高によってレイヤー操作が画面外へ移動する
3. **主要コマンドが不可視** — Undo / Redoの実行可否が画面から分からない
4. **色が意味ではなく場所に紐づいている** — 緑がアクティブツール・全スライダー塗り・選択レイヤーの3役を兼ねている
5. **開発情報と製品情報の混在** — FPS / Latency / Points がキャンバス左上を占有
6. **入力コントロールの窮屈さ** — 240px幅で「テクスチャ」ラベルが折り返している
7. **UI実装の責務集中** — 右ドックの構造とスタイルが `index.html` に集中

追加で確認した問題:

8. **文書境界が判別できない** — 地色とキャンバスの明度差がほぼない
9. **レイヤーリストが規模に耐えない** — 現行の行構造（名前 + 合成モード + 不透明度スライダー、約50px）では、想定枚数100枚で縦5000pxとなり事実上ナビゲートできない

## 2. コンセプト

### 「光を混ぜるための、静かな作業台」

1. キャンバスが常に最も強く見える
2. HDR、発光、リニアカラーを自然に扱える
3. 高機能でも、描画中は必要な操作だけが見える
4. 状態変化は色だけに依存せず、形、ラベル、配置でも伝える

### 2.1 色の役割

| 色 | 用途 |
|---|---|
| ニュートラルグレー | 背景、パネル、通常テキスト、境界、**スライダーの塗り** |
| オレンジ | HDR、クリップ、注意を要する光量情報 |
| 赤 | 破壊的操作、エラー |

**緑は廃止する。** 理由は2つ。

- 光を扱うアプリで唯一の有彩アクセントが「光」を指すのは意味が通る。緑は現状どの概念にも対応していない
- 現状8本のスライダーがすべて緑であり、緑は「選択中」を意味していない

**選択状態は色相ではなく明度と形で表す。** 具体的には、背景を1段明るくし、左端に2pxのバーを立てる。これは原則4「色だけに依存しない」の実践でもある。青いパネル見出し色も廃止する。

### 2.2 キャンバス地色（カラーマネジメント決定）

キャンバス周囲の地色は装飾ではなく**画像の見えに影響する要素**であるため、以下を仕様として固定する。

- 低彩度・無彩色に限定する
- 明度は中間グレー相当で固定する
- **テーマ切り替えの対象から除外する**

キャンバスには細い境界線を付け、文書範囲を常に判別可能にする。

## 3. レイアウト

```text
┌──────────────────────────────────────────────────────────────┐
│ ファイル名   Undo  Redo      表示倍率      保存状態・書き出し │  40px
├──────┬─────────────────────────────────────┬─────────────────┤
│      │                                     │ ツール          │  156px
│      │                                     ├─────────────────┤
│ 道具 │             キャンバス              │ カラー          │  200px
│      │                                     ├─────────────────┤
│      │                                     │                 │
│      │                                     │ レイヤー        │  flex: 1
│      │                                     │                 │
├──────┴─────────────────────────────────────┴─────────────────┤
│ ズーム / 回転 / 表示変換                 ステータス・警告   │  28px
└──────────────────────────────────────────────────────────────┘
```

### 3.1 右ドックをタブにしない理由

描画の基本ループは「描く → レイヤーを変える → 描く」であり、1セッションで数百回まわる。タブは相互排他であるため、このループのたびにツール設定が消える。

より本質的には、**レイヤーパネルの主機能は操作ではなく状態表示**である。イラストソフト最大の事故は「違うレイヤーに描いた」であり、これはアクティブレイヤーが常時見えていることでしか防げない。ツール設定は逆に結果がストロークに現れるため、値を確認する必要が薄い。

したがって、**隠してよいのはツール設定側であり、レイヤーは常時表示とする。**

### 3.2 縦の配分（ウィンドウ高800px、ドック幅240px）

| ゾーン | 高さ | 内訳 |
|---|---|---|
| コマンドバー | 40 | ファイル名 / Undo・Redo / 保存状態 |
| ツール | 156 | ヘッダ28 + 主要3行×28 + 詳細ヘッダ28 + 余白 |
| カラー | 200 | SV + Hue + EV + 色チップ + 保存色 |
| **レイヤー** | **376（`flex: 1`）** | 操作ストリップ32 + 共有ストリップ32 + リスト312 |
| ステータスバー | 28 | ズーム / 表示変換 / HDR警告 |

ツールとカラーは内容が固定長のため content-height とし、**レイヤーゾーンのみが残り高さを吸収する。** ウィンドウを縦に伸ばした利益はすべてレイヤーに配分される。

800px時点でリストは26px行×12行、1440px高では約36行が可視となる。

### 3.3 上部コマンドバー

- ファイル名
- Undo / Redo（有効・無効状態を表示）
- 保存状態
- 開く / 保存
- PNG書き出し

アクティブレイヤーのクリアなど対象を誤りやすい操作は常設せず、メニューまたは確認付き操作へ移す。

### 3.4 左ツールバー

現行のカテゴリ分けとショートカットを維持する。OS依存の絵文字は統一された単色SVGアイコンへ段階的に置き換える。既存の安定IDとショートカットは維持する。

### 3.5 下部ステータスバー

ズーム / 回転・反転 / 表示変換（ポップオーバー） / HDRクリップ警告 / 一時通知。

FPS、Latency、Points は開発モードまたは診断パネル内だけに表示する。

## 4. レイヤーパネル設計

### 4.1 原則

**N行に同じコントロールをN個置かず、共有ストリップ1本に集約する。**

想定枚数は数十〜100前後。現行の行構造をこの規模へ拡大することはできない。

### 4.2 構造

```text
┌ レイヤー ─────────── [+] [フォルダ] [複製] [削除] ┐  32px
├──────────────────────────────────────────────────┤
│ 通常 ▾    不透明度 ━━━●━━ 100%    🔒 α  🔒       │  32px ← 選択レイヤーのみ
├──────────────────────────────────────────────────┤
│ ▾ 📁 髪                                      👁  │  26px
│   ▪ [◧] ハイライト                           👁  │  26px  ← 背景に不透明度の帯
│   ▪ [◧] 影                                   👁  │
│ ▸ 📁 顔                                      👁  │
└──────────────────────────────────────────────────┘
```

### 4.3 行の規則

- **行高26px固定**
- **合成モードは行から除去し、選択レイヤーの共有ストリップへ移す。** 光ベースに再編した合成モードは項目数が多く、240px幅のドロップダウンを各行に置く構造は元々破綻している
- **不透明度は行の背景に薄い塗り帯として表示する。** hover / 選択時のみドラッグ可能。各行で不透明度が見えるという要件を保ったまま、行高コストをゼロにする
- **サムネイル20pxは省略しない。** 100枚を名前だけで識別することはできず、CSP移行組が最初に探す要素である
- **幅配分**: インデント12 + twisty12 + サムネイル20 + 名前（可変） + ロック16 + 目16。深さ2でも名前に約124px残る
- **検索 / フィルタ欄は常設しない。** 28pxは可視12行のうち1行に相当する。Ctrl+Fで一時表示とする

### 4.4 グループ行

- **twistyはグループ行のみ。** インデント10px + 縦のガイド線
- 240px幅では深さ3が実用限界。階層数の制限は設けず、深いときのみリスト上端にパンくずを表示する
- **不透明度の背景帯はグループ行にも適用する**（4.5によりグループ不透明度が厳密に定義されるため、子と意味が揃う）
- **非表示グループの子は、暗くした目アイコン + 行全体の減光で継承を示す。** 子自身の可視状態は保持する

### 4.5 グループの定義

グループは **premultiplied float32 RGBA の独立バッファへ合成し、その結果を親へ1枚として渡す**（isolated）。

**Pass Through（通過）は実装しない。**

通常のアプリでPass Throughが既定である理由は、グループ化しただけで絵が変わると事故になるためである。8bitでは中間バッファに落とした時点でクリップし、背景を参照する合成モードの結果もずれる。

**PhotonMixerではこの前提が成立しない。** 光ベースの主要モード（加算、over）はいずれも結合則を満たし、float32リニアには丸めもクリップもない。`(A over B) over C = A over (B over C)` が厳密に成立するため、**グループ化しても絵は変化しない。** Pass Throughが解決していた問題そのものが存在しない。

例外は Overlay、覆い焼き、ソフトライトなど背景を非線形に参照するレガシーモードのみ。これらは既に副次セクションへ格下げ済みであり、「グループの中は独立した場面。レガシーモードはその中だけを見る」の一文で説明が閉じる。

**制約条件**: グループバッファはアルファを保持すること（premultiplied必須）。不透明背景に焼くと結合則が壊れる。

### 4.6 効果レイヤー

**効果レイヤーは、自分が属するグループ内の下方すべてに作用する。**

この定義により次が成立する。

| 概念 | 実体 |
|---|---|
| グループ | 入れ子の場面 + その結果への効果チェーン |
| ルート（文書全体） | 最上位のグループ |
| **撮影スタック** | **ルートグループの最上部に置かれた効果レイヤー群** |

撮影スタックは新機構ではなく、**効果レイヤーの適用範囲がルートになったもの**である。専用のデータ構造もUIも設けない。ここを別物として設計すると同じものを2回作ることになる。

**表示上の扱い**: セル撮影の撮影台は概念上「絵の外側の工程」であり、同じリストに並べると工程の区別が消える。データ構造は他の効果レイヤーと同一のまま、**ルート効果レイヤーのみリスト最上部に固定表示し、罫線1本で区切る**ことで視覚的にのみ工程を分ける。

効果レイヤーは**専用のサムネイル形状**（正方形ではなく菱形など）で通常レイヤーと即座に区別する。100枚の中で効果を探せることが重要である。

## 5. カラーパネル設計

必須機能を維持したまま200pxへ収める。削るのは面積であり機能ではない。

| 要素 | 現状 | 改定後 |
|---|---|---|
| SVスクエア | 200×103 + 下に水平Hueバー | 176×110 + **右に垂直Hueバー16px** |
| EVスライダー | 全幅 | **全幅を維持。縮小しない** |
| 色チップ（linear / tonemap併記） | RGB数値1行 | 維持 |
| 保存色 | ボタンのみ | 16pxチップの横スクロール1段 |

Hueバーを垂直化して横へ置くことで約20px、保存色を1段固定とすることで約20px確保できる。

**EVスライダーはPhotonMixerの差別化そのものであり、ここを縮めると縮小の意味が反転する。** SDR / HDR の分割表示、境界マーカー、HDR領域の発光トラックは既定通り維持する。

## 6. ツール設定の情報階層

### 常時表示（1段レイアウト）

- サイズ
- 不透明度
- 補正
- カラーへの導線

### 詳細設定（2段レイアウト: ラベル上段 / コントロール下段）

補正方式、後補正、筆圧カーブ、混色方式、にじみ、テクスチャ、テクスチャスケール。

前版で「全行を2段にする」としたが撤回する。100枚のレイヤーを収めるには縦が足りず、折り返しが発生していたのは「テクスチャ」など詳細側のラベルのみであるため。

消しゴム、ぼかし、直線も同じレイアウト規則を用い、各ツールに存在する設定だけを表示する。既存の `TOOLS` / `PARAM_DEFS` / `ToolSettingsStore` は引き続きSSOTとして扱う。

## 7. 維持する操作契約

UI再設計で次の振る舞いを変更しない。

- B / E / U / V / I / G / M / W / T のツールショートカット
- Ctrl+Z / Ctrl+Y による1操作単位のUndo / Redo
- ツールごとのサイズ、補正、不透明度などの個別保持
- 描画色はツール間で共有
- アクティブレイヤー単位の履歴
- ペン入力、筆圧、補正、後補正の描画経路
- キャンバス、選択オーバーレイ、ブラシカーソルの入力契約
- 既存の安定DOM ID。変更が必要な場合はKamox手順と同時更新する

## 8. 実装フェーズ

### Phase 0: 現状の基準を固定

- 現行画面のKamoxスクリーンショットを保存
- 主要操作の確認シナリオを整理
- CSSの現行色、余白、高さを一覧化
- UI変更前のビルド・テスト結果を記録

製品コードを変更しない。

### Phase 0.5: レイヤーモデルへのグループ追加 ← 新設・UI着手の前提

**これはUI作業ではなく、仕様とレンダラ側の作業である。**

1. レイヤーモデルにグループを追加（isolated / premultiplied float32 / アルファ保持）
2. 効果レイヤーの適用範囲を「所属グループ内の下方」に確定
3. グループ合成のタイル単位実装

**制約**: 4096² の float32 RGBA は1枚268MB。グループごとに全面バッファを持つ設計は成立しない。**グループ合成もタイル単位・ダーティ矩形のみ**とする。これは `.pmx` のタイルEXR構造と整合するが、レンダラ側の決定事項として記録が必要。

Phase 0.5 を飛ばしてUIだけ進めると、レイヤー行の構造を2回書くことになる。

### Phase 1: アプリシェルの再配置とレイヤーパネル再構築

- 上部コマンドバーを追加
- Undo / Redo を可視化
- ファイル操作を右ドックから移動
- **右ドックを3ゾーン化し、レイヤーゾーンを `flex: 1` にする**
- **レイヤー行から合成モードのドロップダウンを除去し、共有ストリップへ移す**
- **行高26px固定、サムネイルを追加、グループ行を実装**
- 下部ステータスバーを追加
- 開発モニターを通常表示から外す

レイヤー行の再構築は「置き場所の変更」ではなくパネルの作り直しであるため、後段フェーズに置かずここで行う。

### Phase 2: 最小デザインシステム

CSS変数または専用モジュールで定義する。

- 背景色と階層（キャンバス地色を含む）
- 文字色 / 境界色 / 状態色
- 4px / 8px基準の余白
- コントロール高 / 角丸 / フォーカスリング
- Hover / Active / Disabled / Danger 状態

既存の `.tool-btn` と `.ctrl-row` を共通コンポーネントへ寄せる。

### Phase 3: コンテキストインスペクター

- ツール設定を主要 / 詳細へ分離
- 不要な設定を完全に非表示
- 数値入力の幅と単位表示を統一
- 選択、移動、変形には操作ヒントと確定 / 取消を優先表示
- 詳細セクションの開閉状態を保持

### Phase 4: カラーと表示操作

- カラーパネルを5節の構成へ改定
- 表示変換をステータスバーのポップオーバー化
- HDR / クリップ状態をステータスバーへ反映

### Phase 5: アイコンと仕上げ

- 絵文字をSVGへ置換
- Tooltipへ名称とショートカットを表示
- キーボードフォーカス順を整理
- 狭いウィンドウでの表示確認
- 色覚だけに依存しない状態表現を確認

## 11. Kamox確認ゲート

- キャンバスが従来より狭くならない
- 1240×800でもコマンドが重ならない
- 新規キャンバスダイアログがアプリシェルより前面に出る

### 描画

- ブラシで描画できる / 消しゴムで消去できる
- 描画 → 消しゴム → Undo / Redo が一致する
- ツール切り替え後も個別設定が復元される
- ペン補正と後補正の設定が維持される
