# PhotonMixer 基盤・UI段階刷新計画 v3

更新日: 2026-07-31  
状態: 実装前レビュー用

前版は [`ui-redesign-plan-v2.md`](./ui-redesign-plan-v2.md) として保存する。

## 1. 目的

PhotonMixerのUIを短期的に整えるだけでなく、レイヤーシステム、タイル描画、合成、
保存形式まで段階的に再構築し、その上に最終UIを成立させる。

短期UIでは「すぐ見栄えがするが後で捨てるもの」を作らない。最終UIでも使うアプリシェル、
コマンドバー、ステータスバー、デザイントークン、コンポーネント境界だけを先に整える。

一方、グループ行、サムネイル、階層移動など内部モデルに強く依存するUIは、基盤完成後に実装する。

## 2. 基本方針

1. 各Phase終了時点で、PhotonMixerを実際に描画へ使える状態に保つ
2. UI、文書モデル、レンダラー、保存形式を一度に変更しない
3. 先に意味を決め、次にデータモデル、その後にGPU実装とUIを接続する
4. 既存の一操作Undo、ツール設定、ショートカットを保護する
5. 自動テストだけでなく、Kamoxで実際の制作操作を確認する
6. 各コミットをビルド可能、確認可能、単独で戻せる境界にする

## 3. 最終コンセプト

### 「光を混ぜるための、静かな作業台」

- キャンバスを常に最も強く見せる
- HDR、発光、リニアカラーを自然に扱える
- 描画中は必要な操作だけを見せる
- 状態を色だけに依存せず、形、ラベル、配置でも伝える
- 多数のレイヤーと効果を扱っても、現在の描画対象を見失わない

### UIクロームの色

| 色 | 用途 |
|---|---|
| ニュートラルグレー | 背景、パネル、通常テキスト、境界、通常スライダー |
| オレンジ | HDR、クリップ、光量に関する注意 |
| 赤 | 破壊的操作、エラー |

緑はUIクロームの状態色・アクセント色として使用しない。作品、カラーピッカー、
カラーチップ内の緑は対象外とする。

キャンバス周囲の地色は無彩色とし、表示変換やView EVの影響を受けないUI色として扱う。
具体的なsRGB値と境界色はPhase 1の視覚確認で確定する。

## 4. 全体ロードマップ

```text
Phase 0   設計境界と性能目標の確定
   ↓
Phase 1   無駄にならない短期UI基盤
   ↓
Phase 2   文書・レイヤーモデル v2
   ↓
Phase 3   タイル描画基盤
   ↓
Phase 4   グループ・効果・合成システム
   ↓
Phase 5   保存形式・履歴・大規模文書対応
   ↓
Phase 6   新レイヤーUI
   ↓
Phase 7   最終UI統合
```

## 5. 維持する操作契約

全Phaseを通して次を維持する。

- B / E / U / V / I / G / M / W / T のツールショートカット
- Ctrl+Z / Ctrl+Yによる一操作単位のUndo / Redo
- ツールごとのサイズ、補正、不透明度などの個別保持
- 描画色はツール間で共有
- ペン入力、筆圧、補正、後補正の描画経路
- キャンバス、選択オーバーレイ、ブラシカーソルの入力契約
- 既存の安定DOM ID。変更時はKamox手順も同時更新する
- 表示操作は作品データを変更しない
- リニアHDRデータと表示変換を分離する

レイヤー構造操作のUndoはPhase 0で意味を決め、Phase 2以降の契約へ追加する。

## Phase 0: 設計境界と性能目標の確定

### 目的

後から変更するとデータ、表示、保存形式のすべてへ影響する項目を、実装前に決める。

### 決定対象

#### レイヤーとグループ

- グループの合成意味
  - isolated
  - Pass Through
  - 両方を持つ
- グループ作成前後で表示が一致する条件
- 表示が変化する合成モードと、そのユーザーへの説明
- グループ不透明度とグループ合成モード
- クリッピングをレイヤー属性として持つか、別ノードとして持つか
- レイヤー構造操作をUndo対象にするか

source-over同士には結合則があるが、Add、Multiply、Screen、Overlay、効果レイヤー、
不透明度を混在させたスタック全体で、isolatedグループ化前後の一致は保証できない。
したがって「常に見た目が変わらない」は前提にせず、代表ケースの期待結果を決める。

#### 効果

- `below`入力の意味
- 特定ペイントレイヤーID入力を維持するか
- 効果レイヤーの適用範囲
- ルート効果を独立機構にするか、通常の効果ノードとして扱うか
- グループ境界を越える参照を許可するか

#### タイル

- タイルサイズ
- タイル境界のフィルター余白
- ダーティ範囲の伝播
- 表示範囲外タイルの保持方針
- GPUテクスチャ再利用
- CPU readbackの許容範囲

#### データ形式

- `.pmx` v2のバージョニング
- v1のフラットレイヤーからRootGroupへの移行
- 未知のノード、効果、合成モードの扱い
- タイルデータを保存するか、読み込み時に再構築するか

#### 現実のデータサイズ

現行GPUテクスチャ形式は `rgba16float` で、1ピクセル8バイト。

```text
4096 × 4096 × 8 bytes = 128 MiB
```

`rgba32float`なら256MiBだが、現在の実装形式ではない。
また、現行`.pmx`はZIP内に生float16データを保存しており、タイルEXRではない。

### 性能目標案

- 4096×4096キャンバス
- 100レイヤー
- 通常のペン描画60fpsを目標
- ペン入力中に全レイヤーをCPUへreadbackしない
- 画面外の全タイルを常時GPU展開しない
- タイル境界に継ぎ目が出ない
- 100レイヤーのUIスクロールで長時間停止しない

### 成果物

- レイヤーモデル設計書
- 合成ケース一覧と期待画像
- タイル描画設計書
- `.pmx` v2移行方針
- 性能計測条件

### 完了条件

代表的なスタックについて、グループ化、効果適用、保存・再読込後の期待結果を説明できる。

## Phase 1: 無駄にならない短期UI基盤

### 目的

現在の使いにくさを軽減しながら、最終UIへそのまま残せる骨格を作る。

### 実装内容

- UIトークン
  - 背景
  - 文字
  - 境界
  - 状態色
  - 余白
  - コントロール高
  - フォーカスリング
- `AppShell`
- 上部`CommandBar`
- Undo / Redoの可視化
- 開く / 保存 / PNG書き出しの移動
- 下部`StatusBar`
- FPS / Latency / Pointsの開発モード化
- キャンバス境界の明確化
- 右ドックをツール / カラー / レイヤーの上下3ゾーンへ整理
- `index.html`から構造とスタイルを段階的に分離

### レイアウト

```text
┌──────────────────────────────────────────────────────────────┐
│ ファイル名   Undo  Redo      表示倍率      保存状態・書き出し │
├──────┬─────────────────────────────────────┬─────────────────┤
│      │                                     │ ツール          │
│      │                                     ├─────────────────┤
│ 道具 │             キャンバス              │ カラー          │
│      │                                     ├─────────────────┤
│      │                                     │ レイヤー        │
│      │                                     │ flex: 1         │
├──────┴─────────────────────────────────────┴─────────────────┤
│ ズーム / 回転 / 表示変換                 ステータス・警告   │
└──────────────────────────────────────────────────────────────┘
```

レイヤーは現在の描画対象を示す状態表示でもあるため、タブで隠さず常時表示する。
ウィンドウ高の増減分は主にレイヤー領域へ配分する。

### このPhaseで作り込まないもの

- グループ行
- レイヤーサムネイル
- ツリー表示
- 仮想スクロール
- 最終レイヤー行デザイン
- 全アイコンのSVG化

既存レイヤーパネルを新しいレイヤー領域へ移し、データモデル依存のUIは作らない。

### 無駄にならない理由

`AppShell`、`CommandBar`、`StatusBar`、UIトークン、3ゾーン構造は最終UIでも使用する。

### コミット境界

1. UIトークン
2. AppShell
3. CommandBarと既存ファイル操作の移動
4. StatusBarと開発モニターの移動
5. 右ドック3ゾーン化
6. Kamox回帰修正

### 完了条件

- キャンバスが従来より狭くならない
- 右ドック全体の長いスクロールがなくなる
- ツール、カラー、アクティブレイヤーが同時に見える
- Undo / Redoの有効状態が見える
- 1240×800で主要コマンドが重ならない
- 既存の描画、消しゴム、レイヤー、保存操作が維持される

## Phase 2: 文書・レイヤーモデル v2

### 目的

UI、GPUテクスチャ、保存形式から独立した文書モデルを作る。

### 目標構造

```text
Document
└─ RootGroup
   ├─ PaintLayer
   ├─ EffectLayer
   └─ GroupLayer
      ├─ PaintLayer
      └─ EffectLayer
```

### 実装内容

- `DocumentModel`
- `LayerNode`
- `PaintLayer`
- `EffectLayer`
- `GroupLayer`
- Stable ID
- 親子関係
- 挿入、削除、移動、入れ子
- 可視性、不透明度、合成モード
- 効果入力と適用範囲
- 構造操作のUndo / Redo
- 現行フラットレイヤーをRootGroup直下へ変換するアダプター

### 移行境界

```text
DocumentModel
    ↓
RenderAdapter
    ↓
現行フラットレンダラー
```

最初はRootGroup直下のペイントレイヤーだけを現行レンダラーへ渡し、モデル移行を先行する。
グループを含む文書は、Phase 4で正式にレンダリング可能にする。

### コミット境界

1. LayerNode型とStable ID
2. DocumentModel
3. 構造操作
4. 構造Undo / Redo
5. 現行レンダラーアダプター
6. 既存フラット文書の移行テスト

### 完了条件

- headlessテストで構造操作を検証できる
- レイヤーを移動してもIDが変わらない
- 一操作Undoが維持される
- 現行文書をRootGroupへ変換しても表示結果が変わらない

## Phase 3: タイル描画基盤

### 目的

グループや多数レイヤーを追加しても、全面サイズの中間テクスチャを無制限に増やさない基盤を作る。

### 実装内容

- タイル座標とタイルID
- タイルキャッシュ
- ダーティタイル管理
- 表示範囲に必要なタイルの選択
- タイル単位の合成
- タイル単位の再ベイク
- タイル境界をまたぐブラシ描画
- フィルターに必要な近傍タイルと余白
- GPUテクスチャ再利用プール
- VRAM使用量の計測

### 段階移行

1. 現行全面テクスチャ経路を維持する
2. 同じ入力をタイル経路へ描画する
3. 画像比較で一致を確認する
4. ペイントレイヤーからタイル経路へ切り替える
5. 全面経路をフォールバックとして残す期間を設ける

### コミット境界

1. タイル座標と範囲計算
2. キャッシュと再利用プール
3. ダーティ管理
4. タイル合成
5. ペイントレイヤー移行
6. 全面経路との画像比較

### 完了条件

- タイル境界に継ぎ目がない
- 画面外の全タイルを常時展開しない
- ストローク時に全レイヤーを再処理しない
- 描画 → 消しゴム → Undo / Redoが全面経路と一致する
- VRAM使用量を計測できる

## Phase 5: 保存形式・履歴・大規模文書対応

### 目的

新しい文書構造を安全に保存し、長時間編集と大規模文書に耐えられるようにする。

### `.pmx` v2保存対象

- フォーマットバージョン
- レイヤーツリー
- グループ
- 効果レイヤー
- Stable ID
- 合成モード
- 効果入力
- View settings
- HDRスウォッチ
- ペイントデータ

### 互換方針

- v1のフラットレイヤーをRootGroup直下へ移行する
- 旧バージョンで開けない場合は明示する
- 未知の効果や合成モードを黙って破棄しない
- 読み込み失敗時に原本ファイルを変更しない
- 保存後にクリーンな再読込で結果を比較する

### 履歴

- 描画履歴
- 構造操作履歴
- グループ移動
- 効果パラメータ変更
- タイル単位の履歴基準
- 履歴上限を超えても既存描画を失わない

### 完了条件

- 保存、終了、再読込後に表示結果と構造が一致する
- v1文書を移行できる
- 長時間編集後もUndoで古い描画を失わない
- 壊れたファイルを黙って部分読込しない

## 7. 実装順序の意図

Phase 1は仮UIではない。最終UIでも残る骨格だけを先に作る。

Phase 2でUIより先に文書の意味を安定させ、Phase 3で多数レイヤーとグループを支えるGPU基盤を作る。
Phase 4で意味と描画を接続し、Phase 5で永続化する。モデルが安定した後にPhase 6のレイヤーUIを作るため、
フラットレイヤー前提のUIを作り直す無駄を避けられる。

最後にPhase 7でPhotonMixer固有のColor EV、表示変換、HDR状態、統一アイコンを含む完成形へ仕上げる。

## 8. AI Cortexへの反映

本書は実装計画であり、次の設計判断はまだ確定扱いにしない。

- isolated / Pass Through
- 効果レイヤーの適用範囲
- クリッピングの表現
- ルート効果の扱い
- タイルサイズとキャッシュ戦略
- `.pmx` v2の保存構造

Phase 0でユーザー確認後、以下を連鎖更新する。

1. `decisions/`: 採用理由
2. `spec`: 確定仕様
3. `context`: 現在地と次の作業
4. 必要な実装上の知見があれば`notes/`
