## エピソード1: なぜWebGPUなのか — Canvas 2Dからの脱却

**コミット: `85ee8e5` Phase 1**

### 背景
最初はCanvas 2Dで作ることも考えたが、以下の理由でWebGPUを選んだ:
- float32リニアカラーでの合成をGPUネイティブでやりたい
- スタンプ方式のブラシ描画はinstanced drawが最適
- 将来的なCompute Shader（ダウンサンプル等）を見据えた

### 初期実装
- PointerEvent → 手ブレ補正（速度連動EMA）→ Catmull-Rom補間 → 筆圧→サイズ変換 → WebGPU instanced draw
- spacing=1px固定で高速描画時の点線を解消（暫定）

### 記事のポイント
「Canvas 2Dでもお絵かきソフトは作れるが、HDR・リニアカラー・非破壊エフェクトをやろうとするとGPU APIが必須になる」という動機説明。

## エピソード2: α蓄積問題との戦い — 隔離バッファ方式の発明

**コミット: `c0c08bb` 隔離バッファ方式**

### 問題
スタンプ方式のブラシで、同じストローク内のスタンプが重なるとαが蓄積して不透明度がおかしくなる。
- 半透明30%のブラシを描いているのに、重なった部分はほぼ不透明になる
- これは「正しい描画」だが、ユーザーの期待と違う（1ストローク=1レイヤーの不透明度）

### 試行錯誤
1. **spacing調整** — スタンプ間隔を広げて重なりを減らす → 線が点線になる
2. **spacing=1pxに戻す** → 点線は消えるがα蓄積が復活

### 解決策: 隔離バッファ
- 全ストロークを毎フレーム `isolatedTexture` に `max blend` で描画
- `max blend` なのでαは蓄積しない（最大値のみ残る）
- canvasには `over blend` で転写
- 同一ストローク内のスタンプ重なりでαが蓄積しなくなった

### 記事のポイント
「GPUのブレンドモードを工夫して、直感的なブラシ挙動を実現した」話。`max blend`という一見非標準的な使い方が、実はお絵かきソフトのα蓄積問題に完璧にマッチした。

## エピソード3: float32リニアカラーへの移行 — 4xスーパーサンプリング

**コミット: `0cc8981` Block 1**

### 背景
rgba8unorm（8bit/チャンネル）ではバンディングが目立つ。特にグラデーションや露出補正で顕著。
→ rgba16float（16bit浮動小数点）に移行したいが、フィルタリングに対応が必要。

### 実装
- `float32-filterable` featureを要求
- 4x解像度のバッファに描画 → Compute ShaderでBox Filterダウンサンプル → 1xに
- これにより、アンチエイリアシング品質が大幅に向上

### 記事のポイント
「8bitでは表現できない色階調を、16bit float + 4xスーパーサンプリングで実現」。
Compute Shaderを使ったダウンサンプルなど、WebGPUならではの手法を紹介。

## エピソード4: Oklab湿式混色 — 知覚的に正確な色混合

**コミット: `6315ae7` Block 2**

### 背景
sRGB空間で色を混ぜると、中間色が暗く・濁る。特に赤と青を混ぜると汚い紫になる。
→ Oklab色空間で混ぜれば、知覚的に自然な中間色が得られる。

### 実装
- `src/color/`: sRGB ↔ リニア ↔ Oklab の変換モジュール
- brush.wgsl: committed_textureから既存色をサンプリング → Oklab空間で混色
- wet_ratio（にじみスライダー）で混色比率を制御

### 記事のポイント
「色空間の選択が描画結果に与える影響」を実例で示せる。
sRGB混色 vs Oklab混色の比較スクショが効く。

## エピソード5: 引きずり混色（progressive mixing）の長い旅

**コミット: `c5c6cc2` 〜 `2d55228`（10コミット以上の試行錯誤）**

これは最もドラマチックなエピソード。1日で10回以上の修正を繰り返した。

### 目標
筆を動かすにつれて、キャンバス上の色を拾って徐々に色が変化する「引きずり」挙動。

### 試行錯誤の軌跡

1. **`c5c6cc2` 初回実装**: pen-down時にcommittedTextureをCPUにスナップショット、moveごとにcanvas色をサンプリングしてOklabで混合
2. **`fb0d3f6` 全点同色問題**: render()が毎フレーム全点を同一uniform colorで再描画するため、色が変化しても全点が同じ色で上書きされる → moveごとに新規点のみコミットする方式に変更
3. **`7358afc` スナップショット全ゼロ問題**: committedTextureにCOPY_SRCフラグがなく、copyTextureToBufferが失敗 → スナップショットが全ゼロで混色が一切動かなかった
4. **`2e161b3` 引きずりすぎ問題**: 色を拾い続けて元の色が消える → Oklab減衰を追加（6%/stepで元の色に戻る）
5. **`7bfa720` 半透明ブラシの点線問題（再発）**: progressiveモードでセグメント境界にギャップ → max blendベイクで解決
6. **`aa700af` 明るいスポット問題**: OVERLAP描画でαが蓄積して明るい点ができる → OVERLAP=0に変更
7. **`1f3ee07` ストローク重なり濃淡崩れ**: 専用蓄積バッファを導入
8. **`81e62c2` 50%+混色の濃淡崩れ**: 点ごとの色方式に刷新して根治
9. **`2d55228` 選択色が消える問題**: smudge/deposit分離方式に変更

### 記事のポイント
「1つの機能の実装に10回以上バグ修正が必要だった」話。
各バグの現象→原因→修正を時系列で並べると、GPUプログラミングの落とし穴がよくわかる。
特に「COPY_SRCフラグ忘れでスナップショットが全ゼロ」はWebGPUあるある。

## エピソード7: レイヤーシステムと非破壊エフェクト

**コミット: `f6bce6c` Block 5, `4ad3510` 〜 `ed333d7` フィルター・エフェクト**

### レイヤーシステム
- 各レイヤーがcommitted GPUTextureを持つ
- 合成シェーダー（blend.wgsl）で複数レイヤーをブレンド
- 通常/乗算/スクリーン/オーバーレイ/加算のブレンドモード

### 非破壊エフェクト
- ぼかし・グロー・シャープ・露出・レベル補正・トーンカーブ
- エフェクトレイヤーとして重ねる → 元レイヤーを破壊しない
- フィルターはマルチパス（tmpA → tmpB → 最終合成）

### 記事のポイント
「Photoshopライクな非破壊編集をWebGPUで実現」。
エフェクトのマルチパス処理など、GPUパイプラインの設計が見どころ。

## エピソード10: Electron化とパッケージEXEの罠

**コミット: `fae8b22`, `8e0ad98`**

### 罠1: シェーダーパス
- 開発時は `fetch('shaders/brush.wgsl')` で動く
- パッケージ化すると `app.asar` 内のパス構造が変わり `ERR_FILE_NOT_FOUND`
- 修正: 全シェーダーのfetchパスを `dist/shaders/` に変更（6ファイル）

### 罠2: DevTools
- 本番EXEでDevToolsが開いているとユーザーが混乱する
- `process.env.PM_DEV` でのみ開くよう分離

### 罠3: playwright-coreの不要同梱
- 依存に残っていたplaywright-coreがアプリ未使用なのにパッケージに混入
- dependenciesから除去

### 記事のポイント
「Webアプリをデスクトップアプリにする際の落とし穴」。
ファイルパス・asar・不要依存の削除など、実践的な知見。

## エピソード11: バグ修正2題 — スナップショットとバケツ塗り

**コミット: `fae8b22` デバッグ**

### Bug 1: スナップショットのサイズ不一致
- `buildColoredStroke` が `sampleSnapshot` に画面サイズ（`renderer.canvas.width`）を渡していた
- 正しくはドキュメントキャンバスサイズ（`viewport.getCanvasSize()`）
- ズーム時にサンプリング座標がずれて混色が崩れる

### Bug 2: バケツ塗りが選択範囲を無視
- フラッドフィルが選択マスクを考慮していなかった
- `inSelection()` ヘルパーを追加し、左右スキャン・上下スタック両方に統合

### 記事のポイント
「画面座標とキャンバス座標の混同」はお絵かきソフトあるある。
選択マスクの境界処理など、フラッドフィルの実装詳細が見どころ。
